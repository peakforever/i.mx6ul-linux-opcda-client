规格:docs/dev-spec-iter1.md
状态:待 Codex 开工

## 迭代 2:多 Item 采集 + OPC2ECU UDP 发送

目标:实现原 Windows 程序的替代品——多 Item 周期采集、30 字节小端记录、
48 条/报文组包、UDP 发送到 ECU 转发目标。

依赖:迭代 1 完成。编码器(EcuRecordCodec)已就绪并有固定字节向量自测。
关键设计点(开工时细化):
- 多 Item 配置格式(点位表):等同事驱动框架规范定案后对齐;先按 properties
  多 item 列表或简单 JSON 过渡
- 采集循环:单 Group 多 Item SyncAccess 或 Async20Access,周期统一
- 组包:满 48 条或到 flush 周期即发;MD5 输入字符集按现场 Windows ACP 配置
- 丢包/背压:UDP 发送失败时的记录策略(丢弃/落盘/计数)
- 与工作台(Go)的接口:数据面走 UDP,控制面后续定

## 迭代 3:驱动框架适配层 + 配置格式对齐

目标:按同事的驱动框架标准协议规范,把采集核心包装成标准驱动形态:
- 适配层接口(规范定义的配置格式、启停、状态上报、异常上报)
- 平台填表配置 + 点位表导入格式对接
- 与网关管理平台/工作台(Go Web 服务)的进程内/进程间集成方式定案

依赖:同事规范文档(契约,最优先,等稿中)。
注意:迭代 1/2 的核心代码与适配层解耦,规范到位后只新增适配层,不改核心。

## 贯穿性工程要求

- Java 8 字节码目标(网关 Zulu JRE 8 compact1),Maven 构建,单元测试随代码
- 256MB RAM 约束:JVM -Xms16m/-Xmx48m 起步,新增功能保持内存敏感
- 安全:密码只走环境变量/密钥文件,配置不入库,日志不打印凭据
- 每个迭代结束:实机验收(网关↔Windows+Matrikon)+ 资源实测记录
- 提交规范:英文 summary,功能/测试/文档分 commit
