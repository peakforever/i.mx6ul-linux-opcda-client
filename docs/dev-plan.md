## 迭代 2:多 Item 采集 + OPC2ECU UDP 发送

目标:实现原 Windows 程序的替代品——多 Item 周期采集、30 字节小端记录、
48 条/报文组包、UDP 发送到 ECU 应用。

依赖:迭代 1 完成。编码器(EcuRecordCodec)已就绪并有固定字节向量自测。
关键设计点(开工时细化):
- 发送目标=本机回环(默认 127.0.0.1 + ECU 应用 UDP 端口),配置项
  udp.targetHost / udp.targetPort;行为与 Windows 版 opc2ecu 逐字节一致
- 多 Item 配置格式(点位表):等同事驱动框架规范定案后对齐;先按 properties
  多 item 列表或简单 JSON 过渡
- 采集循环:单 Group 多 Item SyncAccess 或 Async20Access,周期统一
- 组包:满 48 条或到 flush 周期即发;MD5 输入字符集按现场 Windows ACP 配置
  (中文点名通常 GBK,必须与 ECU C++ 应用预期一致)
- 丢包/背压:UDP 发送失败时的记录策略(丢弃/落盘/计数)

## 迭代 3:驱动框架适配层 + 配置格式对齐

目标:按同事的驱动框架标准协议规范,把采集核心包装成标准驱动形态:
- 适配层接口(规范定义的配置格式、启停、状态上报、异常上报)
- 平台填表配置 + 点位表导入格式对接
- 与网关管理平台/工作台(Go Web 服务)的进程内/进程间集成方式定案

依赖:同事规范文档(契约,最优先,等稿中)。
注意:迭代 1/2 的核心代码与适配层解耦,规范到位后只新增适配层,不改核心。

## 集成架构定案(2026-08-20)

背景:原架构中 OPC 采集由部署在 OPC server 主机上的 Windows 应用 opc2ecu
完成,经以太网 UDP 把 30 字节记录发到 ECU 网关;ECU 内 C++ 应用的驱动数据
走全局变量(紧耦合),无法直接挂接新驱动。

定案:OPC DA client(本 Java 工程)作为网关上的独立进程,以 OPC2ECU UDP
协议与 ECU C++ 应用通信——协议边界、记录格式、组包规则与 Windows 版
opc2ecu 完全一致,发送目标为本机回环(127.0.0.1 + ECU 应用 UDP 端口)。
ECU C++ 应用零改动。

含义:
- 数据面:UDP 报文(30B 记录 × ≤48/报文),与 C++ 应用既有接收逻辑无缝衔接
- 控制面/配置面:点位表、启停、状态上报走后续定的机制(平台/工作台),不占
  用 UDP 数据面
- 写操作:2026-08-20 客户确认不要求,所有迭代均不做(需求变更除外)
- 与工作台(Go)的关系:工作台是测试工具,本工程是生产驱动;两者都可能在
  网关共存,资源预算按 256MB 统筹

## 贯穿性工程要求

- Java 8 字节码目标(网关 Zulu JRE 8 compact1),Maven 构建,单元测试随代码
- 256MB RAM 约束:JVM -Xms16m/-Xmx48m 起步,新增功能保持内存敏感
- 安全:密码只走环境变量/密钥文件,配置不入库,日志不打印凭据
- 每个迭代结束:实机验收(网关↔Windows+Matrikon)+ 资源实测记录
- 提交规范:英文 summary,功能/测试/文档分 commit
